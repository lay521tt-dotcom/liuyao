## 1. 总体架构

```
┌─ 用户浏览器(H5) ─────────────────────────────┐
│  UI 层 (Vue3 + Vite, 移动优先)               │
│  ├─ 手势模块 gesture/                        │
│  ├─ 页面 P1~P6                               │
│  ├─ 排盘引擎 hexagram-core/ (纯TS函数库,无副作用) │
│  ├─ 干支历模块 ganzhi-calendar/              │
│  ├─ 静态数据快照 data-snapshot.json (构建时生成) │
│  └─ 本地存储 localStorage(历史/设置)          │
└──────────────┬───────────────────────────────┘
               │ HTTPS (仅少量请求)
┌──────────────▼───────────────────────────────┐
│  后端 (Node.js + Fastify, 极轻)              │
│  ├─ GET /api/content/version  内容版本检查    │
│  ├─ GET /api/content/snapshot 内容快照(CDN缓存)│
│  └─ POST /api/stats/event    匿名埋点(P1)     │
└──────────────┬───────────────────────────────┘
┌──────────────▼───────────────────────────────┐
│  PostgreSQL：内容库(唯一数据源头)              │
│  构建脚本: DB → data-snapshot.json → 前端打包  │
└──────────────────────────────────────────────┘
```

要点：
- **排盘全部在前端完成**，掷爻随机数用 `crypto.getRandomValues`，弱网/离线可完整走完核心流程
- 数据库是内容唯一源头（Single Source of Truth），前端快照由构建脚本 `npm run export-snapshot` 从库导出，禁止任何人手改 JSON
- V3 加账号时，后端在同一 PostgreSQL 上扩 `user`、云端 `divination_record` 表即可，前端历史模块已按可同步结构设计（见 4.8）

## 2. 技术选型

| 项 | 选型 | 理由 |
|---|---|---|
| 前端 | Vue3 + TypeScript + Vite + Pinia | H5 生态成熟，TS 强类型保护卦理数据结构 |
| 样式 | Tailwind CSS + 自定义水墨主题 token | 移动优先效率 |
| 动效 | CSS transform + requestAnimationFrame；铜钱用 CSS 3D，不引入重型引擎 | 控制包体积 |
| 排盘引擎 | 独立 workspace 包 `hexagram-core`（纯函数，零 DOM 依赖） | 可单测、可被未来后端复用 |
| 干支历 | 自研 `ganzhi-calendar`（基于查表的节气数据 1950–2050 + 干支推算），23点换日 | 口径可控可测，避免第三方库口径不明 |
| 后端 | Node.js 20 + Fastify | 轻量，与前端同语言 |
| 数据库 | PostgreSQL 15 | 标准可靠，V3 可平滑扩展 |
| 部署 | 前端静态托管+CDN；后端单容器 | 成本最低 |

## 3. 模块划分与职责

### 3.1 hexagram-core（核心包，黄金用例的测试对象）
对外只暴露一个主函数：

```ts
paiPan(input: PaiPanInput): PaiPanResult

interface PaiPanInput {
  yaos: [YaoValue, YaoValue, YaoValue, YaoValue, YaoValue, YaoValue]; // 初爻→上爻
  // YaoValue: 6=老阴 7=少阳 8=少阴 9=老阳 (传统记法)
  datetime: string; // ISO, 起卦时间(本地时区)
  question?: { category: Category; text?: string };
}

interface PaiPanResult {
  benGua: GuaInfo;          // 本卦
  bianGua: GuaInfo | null;  // 变卦(无动爻为null)
  siZhu: { year: GanZhi; month: GanZhi; day: GanZhi; hour: GanZhi };
  xunKong: [DiZhi, DiZhi];  // 旬空
  yueJian: DiZhi; riChen: GanZhi;
  lines: LineInfo[6];       // 自初至上
}
interface GuaInfo { id: number; name: string; palace: Palace; palaceIndex: number; // 本宫/一世..归魂
  symbol: string; upperTrigram: Trigram; lowerTrigram: Trigram; }
interface LineInfo {
  position: 1|2|3|4|5|6;
  yinYang: 'yin'|'yang'; isMoving: boolean;
  naJia: { gan: TianGan; zhi: DiZhi; wuXing: WuXing };
  liuQin: '父母'|'兄弟'|'子孙'|'妻财'|'官鬼';
  liuShen: '青龙'|'朱雀'|'勾陈'|'腾蛇'|'白虎'|'玄武';
  shiYing: 'shi'|'ying'|null;
  isXunKong: boolean; isYueBreak: boolean;
  changedYinYang: 'yin'|'yang'|null; // 动爻变后
}
```

内部计算流水线（每步独立函数，独立单测）：
```
yaos → ① 求本卦/变卦卦象id → ② 查 hexagram 表得卦宫/世应
     → ③ 查 najia 表装干支五行 → ④ 按卦宫五行算六亲
     → ⑤ datetime → ganzhi-calendar 得四柱(23点换日)
     → ⑥ 日干起六神 → ⑦ 日柱定旬空 / 月建定月破 → 组装 PaiPanResult
```
规则依据为产品说明书第 5 章。**②③ 必须查静态数据表，禁止运行时推导卦宫与纳甲。**

### 3.2 ganzhi-calendar
`toSiZhu(datetime): SiZhu`。月柱按节气分界（节气表为静态数据，由数据工程师提供 1950–2050 精确到分钟）；日柱 23:00 换日；时柱按时辰。独立黄金用例 ≥30 条（含 23:00 边界、节气交接当天、跨年立春）。

### 3.3 gesture/（前端手势模块）
按交互说明书第 4 章实现三层手势，输出统一事件 `onThrow()`。**手势参数（阈值/冷却）集中在 config 常量文件**，便于测试期调参。手势模块与随机数模块物理分离：`onThrow()` 不携带任何力度参数，掷爻结果只来自 `random.ts` 的 `throwCoins(): YaoValue`（实现见 6.2 概率规范）。

### 3.4 content/（前端内容模块）
从打包的 data-snapshot.json 读卦辞/爻辞/注解；启动时静默请求 `/api/content/version`，有新版本则后台拉取新快照存 localStorage 覆盖使用（离线时跳过）。

### 3.5 storage/（本地历史）
localStorage，key `liuyao_history_v1`，上限 200 条 FIFO。记录结构与未来云端表字段一一对应（见 4.8），保留 `uuid` 与 `synced:false` 字段为 V3 同步预埋。

## 4. 数据库设计（数据工程师按此建表）

命名：snake_case；所有表带 `created_at/updated_at`；内容表带 `version` 字段。

### 4.1 trigram 八卦表（8 行）
`id PK(1-8), name(乾..兑), symbol, wu_xing, binary_code char(3)` — binary_code 自下而上，阳1阴0，如乾=111

### 4.2 hexagram 六十四卦表（64 行）
`id PK(1-64 通行卦序), name, symbol_unicode, upper_trigram_id FK, lower_trigram_id FK, binary_code char(6), palace_trigram_id FK(所属卦宫), palace_index smallint(0本宫,1-5一至五世,6游魂,7归魂), shi_position smallint(1-6), ying_position smallint(1-6), gua_ci text(卦辞原文), gua_annotation text(白话注解), modern_annotation text(现代解读·原创, V1.1甲方需求新增)`
约束：binary_code 唯一；shi/ying 相隔两位 CHECK。

### 4.3 najia 纳甲表（64卦 × 6爻 = 384 行）
`id PK, hexagram_id FK, line_position smallint(1-6), tian_gan, di_zhi, wu_xing, UNIQUE(hexagram_id, line_position)`
> 数据来源：按八宫纳甲定式生成后人工抽核。注意游魂归魂卦纳甲跟随各自内外卦本体，不跟随卦宫。

### 4.4 yao_text 爻辞表（386 行：384 爻 + 乾用九 + 坤用六）
`id PK, hexagram_id FK, line_position smallint(1-6, 用九用六记0), yao_ci text(原文), annotation text(白话注解), UNIQUE(hexagram_id, line_position)`

### 4.5 solar_term 节气表（1950–2050，24×101 行）
`id PK, year, term_name, exact_time timestamptz`

### 4.6 liushen_rule 六神起法表（10 行：日干→初爻六神）与 4.7 xun_kong 旬空表（6 旬 ×2 空亡，60 行展开为日柱→空亡对照）
小表也入库不写死在代码里，保证"数据归数据、逻辑归逻辑"。

### 4.8 divination_record（本期不建后端写入，仅定义结构供本地与 V3 复用）
`uuid PK, question_category, question_text, yaos char(6), datetime_cast timestamptz, paipan_result jsonb(完整PaiPanResult快照), created_at`
> 存 jsonb 快照而非只存输入：保证将来引擎升级后历史记录展示不变。

## 5. 接口定义（本期仅 3 个）

```
GET /api/content/version        → 200 {"version": 3, "snapshot_url": "..."}
GET /api/content/snapshot?v=3   → 200 完整内容JSON (CDN缓存, immutable)
POST /api/stats/event (P1)      → 204  body: {event, ts, anon_id}  无任何个人信息
```
错误格式统一 `{code, message}`；后端不可用时前端核心流程不受影响（快照已打包）。

## 6. 关键实现规范

### 6.1 静态数据纪律
程序员**不得**在代码中手写任何卦宫、世应、纳甲、卦爻辞数据；一律从数据快照读取。代码评审清单第一条检查此项。

### 6.2 随机数规范
```ts
function throwCoins(): YaoValue {
  // 3 枚硬币各自独立: crypto.getRandomValues 取 1 byte, &1 得正/背
  // 背数 3→9老阳 2→8少阴 1→7少阳 0→6老阴
}
```
禁止 `Math.random()`；禁止任何手势参数进入本函数。理论分布 6:1/8, 7:3/8, 8:3/8, 9:1/8。

### 6.3 时区口径
四柱换算一律以用户设备本地时间为准（目标用户中文区）；datetime 存 ISO 含时区偏移。

## 8. 工程结构与里程碑

```
repo/
├─ packages/hexagram-core/   ① 先行开发, 黄金用例通过
├─ packages/ganzhi-calendar/ ① 同步开发
├─ apps/web/                 ② 引擎通过后开发UI
├─ apps/api/                 ② 并行
├─ data/                     数据工程师产出: schema.sql, seed/*.sql, export-snapshot脚本
└─ tests/golden/             测试工程师产出: 黄金用例fixture
```
里程碑：M1 数据库建库+静态数据全量入库并人工抽核 → M2 两个核心包通过全部黄金用例 → M3 UI 完成+E2E 通过 → M4 甲方验收。
**M1、M2 未达标不得进入下一阶段**——排盘引擎错一个字段，UI 做得再好都是废品。
